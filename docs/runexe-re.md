## 1. EXEPACK 解壓（已完成）

`Run.exe` 是 EXEPACK 壓縮的，這一度是靜態分析的最大障礙。現在已可離線解開：

```bash
node --import ./tests/loader.mjs tools/unexepack.mts rich2/original/Run.exe run_unpacked.bin
```

### 檔案結構（實測 `rich2/original/Run.exe`，188382 bytes）

| 項目 | 值 |
|---|---|
| MZ 檔頭 para 數 | 32 → 載入模組起點 **0x200** |
| 檔頭 CS:IP | `2c90:10` → 指向解壓 stub |
| EXEPACK 檔頭位置 | **0x2cb00**（16-byte 版，簽章 `52 42` 'RB' 在 +14） |
| 真正進入點 | CS:IP = `1c6a:55c`，SS:SP = `3235:c00` |
| destLen | 12853 段落 = **205648 bytes** |

### 關鍵：原樣保留區

解壓迴圈跑完 76 個指令後，來源指標與目的指標**收斂在同一位置**（都是 `0x29586`）。
EXEPACK 的設計是：**終止時剩下的低位資料已經在正確位置，原樣不動**。

| 區段 | 檔案 offset | 映像 offset | 對應關係 |
|---|---|---|---|
| **原樣保留區** | `0x200` ~ `0x29786` | `0x0` ~ `0x29586` | **映像 = 檔案 − 0x200（1:1）** |
| 壓縮尾段 | `0x29786` ~ `0x2cb00` | `0x29586` ~ `0x3234f` | 無簡單對應 |

> 這解釋了為什麼直接對原始檔做位元組 patch 會生效——那些 patch 全都落在原樣保留區。
>
> ⚠️ **但壓縮尾段的檔案 offset 不能拿來推算位址**。舊筆記記的「分派器 @0x2a943」就是這個區域的檔案 offset，用它算位址會錯。

### 解壓演算法要點

由尾端往前讀，每個指令：

- `op & 0xFE == 0xB0` → 填充：讀 count(2 byte)、讀 1 byte，重複輸出 count 次
- `op & 0xFE == 0xB2` → 複製：讀 count(2 byte)，複製 count bytes
- `op & 1` → 這是最後一個指令
- **終止後必須把剩餘的來源資料整塊複製到輸出低位**（漏掉這步只會得到 12102 bytes 垃圾）

### 驗證

已知的每張地圖初始化指令，在解壓映像中的位置：

| 指令 | 映像 offset | 檔案 offset |
|---|---|---|
| `MOV word[0x1096], 119`（台灣 maxLoc） | `0x122a6` | `0x124a6` |
| `MOV word[0x1098], 23`（台灣 特殊數） | `0x122ac` | `0x124ac` |
| `MOV word[0x1058], 4`（台灣 玩家數） | `0x122b2` | `0x124b2` |
| `MOV word[0x1096], 140`（香港） | `0x122c0` | `0x124c0` |
| `MOV word[0x1096], 282`（大富翁城） | `0x122da` | `0x124da` |

差值一律 `0x200`，與原樣保留區的對應關係吻合。

## 2. ❌ 已推翻的假設：`CS:0x1482` 不是特殊地點分派器

先前（含更早的筆記）認為映像 `0x2dd2c` 附近是特殊地點分派器，因為它有一張
**11 項**跳轉表、上界檢查是 `CMP BX,10`，剛好對應 11 種特殊地點。

完整反組譯後證實**這是誤判**。該函式（映像 `0x2dd04`，標籤 `0xe884`）：

```asm
e884: mov  bx,[bp+6]        ; BX = 功能編號
e889: cmp  bx,0xff          ; 0xFF → 初始化
e88d: je   e8b3
e88f: cmp  cs:[0x1460],0    ; ==0 直接回傳 0
e895: jne  e89f
e897: xor  ax,ax            ; 回傳 0
e89f: cmp  bx,10
e8a2: jbe  e8ac
e8a4: cmp  cs:[0x1460],2    ; 功能 >10 才要求 ==2
e8aa: jne  e897
e8ac: shl  bx,1
e8ae: jmp  cs:[bx+0x1482]
e8b3: call 0xef04           ; 初始化：算出 cs:[0x1460]
e8b6: mov  cs:[0x1460],ax
```

而 `0xef04`（映像 `0x2e384`）的內容是：

```asm
ef05: mov  bp,0x388         ; ← Adlib/OPL2 標準基底埠
ef0d: mov  ax,0x6004 ; call ; OPL reg04 = 0x60（計時器控制）
ef13: mov  ax,0x8004 ; call ; OPL reg04 = 0x80（IRQ reset）
ef1b: in   al,dx            ; 讀 OPL 狀態
ef20: mov  ax,0xff02 ; call ; OPL reg02 = 0xFF（Timer1）
ef26: mov  ax,0x2104 ; call ; OPL reg04 = 0x21（啟動 Timer1）
ef44: test di,0xe0          ; 檢查狀態位元
```

這是**標準的 Adlib/OPL2 音效卡偵測程序**。結論：

- `CS:[0x1460]` 是**音效卡型別**，不是特殊地點的模式旗標
- `CS:0x1482` 的 11 項表是**音效驅動的功能分派表**
- 「11 項」與「11 種特殊地點」**純屬巧合**
- 同區第二個分派器（`MOV BL,CS:[0x1455]`；`CMP BL,4`；`JMP CS:[BX+0x1478]`，5 項）也在音效驅動範圍內

> **教訓**：只憑「跳轉表項數吻合」就下結論會錯。要追到實際的資料存取（本例是 port I/O）才算數。

## 4. 解 LZEXE 壓縮的執行檔（可重複使用的做法）

專案裡的 `lzexe91e/UNLZEXE5.ZIP` 有 UNLZEXE 0.5 的原始碼與 DOS 執行檔。
那個 zip 是 PKZIP 1.x 的 **implode** 格式，PowerShell 的 `Expand-Archive` 解不開，要用 WinRAR：

```powershell
& "C:\Program Files\WinRAR\WinRAR.exe" x -ibck -y lzexe91e\UNLZEXE5.ZIP lzexe91e\unlzexe5\
```

然後用 DOSBox-X **完全非互動**地跑它：

```powershell
$w = "D:\lzwork"            # 放 UNLZEXE.EXE 跟要解的檔案
$dbx = "D:\dev\rich2_editor\DOSBox-X"
Start-Process -FilePath "$dbx\dosbox-x.exe" -WorkingDirectory $dbx -Wait `
  -ArgumentList '-nomenu -c "MOUNT E D:\lzwork" -c "E:" -c "UNLZEXE JS3.EXE JS3U.EXE" -c "EXIT"'
```

⚠ 兩個踩過的坑：
- **`-c` 的整串指令一定要用引號包成單一參數**。PowerShell 的 `-ArgumentList @("-c","MOUNT E ...")`
  會被拆成好幾個參數，DOSBox 只收到 `-c MOUNT`，其餘當成垃圾參數 —— 結果是靜靜地什麼都不做。
- **`DOSBox-X/dosbox-x.conf` 的 `[autoexec]` 已經把 `rich2` 掛成 C:**，所以要用別的磁碟機代號。

## 6. 找字形點陣：直接抓記憶體快照（建議做法）

> ⚠ 本節「靜態找不到」的前提**已被 §7 推翻**（字形其實在 `Wor.pak` 第 1 組，
> RLE 壓縮過所以直接搜位元組搜不到）。抓記憶體快照這招仍然有效、也確實是破口，
> 步驟保留下來給下次遇到類似問題時用。

靜態找了一整輪都沒找到字形（已排除 `Wor.pak` 全部群組、三張地圖 PAK、`Rich?.rix`(AdLib 音樂)、
`Js3.exe`(搖桿驅動)）。`Run.exe` 確實會讀 `WOR.PAK`，但映像裡找不到可靠的參照
——「`mov dx, offset`」那種寫法在這支程式裡對不上，資料段基底也推不準。

**與其繼續猜檔案格式，不如直接抓執行中的記憶體**：遊戲正在畫中文時，字形一定
以未壓縮的形式躺在 RAM 裡。抓一份 640KB 快照回來搜，比逆推檔案格式可靠得多。

### 步驟

1. 用 DOSBox-X 正常啟動遊戲，走到**畫面上有中文的地方**（例如買地時顯示地名）。
2. 按 **Alt+Pause** 叫出 debugger（另一個 console 視窗）。
3. 在 debugger 打：

   ```
   MEMDUMPBIN 0:0 A0000
   ```

   這會把 0~640KB 整塊倒進 DOSBox-X 的 capture 目錄（預設 `DOSBox-X\capture\`），
   檔名類似 `MEMDUMP.BIN`。
4. 按 **F5**（或打 `RUN`）讓遊戲繼續，關掉遊戲。
5. 把那個 `.BIN` 交出來分析。

### 拿到快照之後要找什麼

- **字形點陣**：639 個字 × 32 bytes（16x16 1bpp）≈ 20KB 的連續區塊，特徵是
  「墨水密度 0.15~0.30、每個字的第一列與最後一列幾乎全 0」。
- **那張 639 項的 Big5 表**：搜 `AA FC A4 67 A5 4A`（阿土仔）。表在記憶體裡的位置
  找到後，**字形陣列多半就在附近**，而且兩者的 index 對應關係可以直接對出來。
- 兩者都找到，就能確定「第 N 個字形」對應「表的第 N 項」，
  之後要換字或加字就只是改這兩塊。

> 💡 若想同時確認「缺字為什麼會掉到表尾」，可以在快照前先在遊戲裡放一個缺字的地名，
> 抓快照時那串文字也會在 RAM 裡，可以一併對照。

## 7. ✅ 字形完全解出來了（2026-07-31）

用 §6 的做法抓到 `DOSBox-X/MEMDUMP.BIN`（640KB，遊戲顯示中文時的 0~A0000），
靠它定出格式後**再回頭比對檔案，發現字形一直都在 `Wor.pak` 裡**——
只是被 RLE 壓過，所以之前直接搜位元組怎麼搜都搜不到。

### 結論一句話

> `Wor.pak` 第 **1** 組解壓後，offset **1664** 起是 **639 個字形**，
> 每個 **30 bytes = 16 寬 × 15 高、1bpp、每列 2 bytes、MSB 在左**，
> 第 *i* 個字形就是第 **4** 組那張 639 項 Big5 字表的第 *i* 個字。**沒有任何中間層。**

### `Wor.pak` 的組成（6 組，指標表在 offset 7）

| 組 | 檔內指標 | 解壓後長度 | 內容 |
|---|---|---|---|
| 0 | `0x27` | 2818 | 未辨識 |
| **1** | `0x941` | **20836** | 前 1664 bytes 未辨識；**offset 1664 起 = 639×30 = 19170 bytes 字形**；尾端剩 2 bytes |
| 2 | `0x5999` | 5482 | 未辨識 |
| 3 | `0x6DA7` | 144 | 未辨識 |
| **4** | `0x6E3B` | **1278** | **639 項 Big5 字表**（`AA FC A4 67 A5 4A` = 阿土仔 開頭，第 638 項 =「邦」） |
| 5 | `0x7345` | 106 | 未辨識 |

解壓用 `src/utils/compression.ts` 的 `decompressGeneralData`，
指標表用 `src/core/parser.ts` 的 `parsePackPointers`，兩支現成的都能直接吃 `Wor.pak`。

### 記憶體中的位置（`MEMDUMP.BIN`）

| 項目 | 位址 |
|---|---|
| 第 1 組載入基底 | `0x5CF80` |
| **字形陣列起點（glyph[0]＝「阿」）** | **`0x5D600`** |
| 字形陣列終點 | `0x62102`（＝ `0x5D600 + 639×30`） |
| 639 項 Big5 字表 | `0x5CA60`（與第 4 組逐位元組相同） |

記憶體那份與 `Wor.pak` 解壓後的內容**逐位元組相同**，所以要改字形改檔案就好，不必碰記憶體。

### 上一版是怎麼錯的（重要，別再踩）

1. **相位差了一列。** 舊筆記拿 `0x5F006` 當基準，但 `0x5F006 % 30 = 26`，
   正確的格子相位是 **24**。差 2 bytes（正好一列）的結果是每一格都由
   「上一個字的最後一列 + 這個字的前 14 列」拼成 —— 畫出來當然是
   「真的中文字，但不是那個字」，而且看起來像被剪切（shear）過。
2. **因為相位錯，「找不到『一』」的搜尋也就必然落空。** 相位對了以後，
   「一」就在 `0x5D90C`（＝ `0x5D600 + 26×30`，字表 index 正好 26），
   而且它是整區**筆畫量最少**的格子（ink=16），用「找 ink 最小的格」一秒就能撈到。
3. 「字形不在任何資料檔裡」是**誤判**。搜不到是因為 `Wor.pak` 存的是 RLE 壓縮流，
   只有極短的巧合片段（「阿」的前 66 bytes）會以原樣出現在檔案裡。

> **教訓**（同 §2）：對齊／相位錯 1 個單位，所有下游的形狀判準都會失效，
> 而且失效的樣子很像「格式猜錯」。先用**單一已知樣本**（這裡是「一」＝最少筆畫）
> 把相位釘死，再談排列方式。

### 怎麼畫（已驗證）

```js
const fs = require('fs');
const b  = fs.readFileSync('DOSBox-X/MEMDUMP.BIN');   // 或 Wor.pak 第1組解壓後的 Buffer
const BASE = 0x5D600, ST = 30;                        // 檔案版的話 BASE = 1664
const T = 0x5CA60;                                    // 字表；檔案版用第 4 組
const d = new TextDecoder('big5');
const table = Array.from({length:639}, (_,i)=> d.decode(b.slice(T+i*2, T+i*2+2)));

function art(i){                                      // 一格 = 30 bytes = 16寬 x 15高
  const o = BASE + i*ST;
  for(let y=0;y<15;y++){
    let s='';
    for(let x=0;x<16;x++){
      const v = b[o + y*2 + (x>>3)];
      s += ((v >> (7-(x&7))) & 1) ? '██' : '　';
    }
    console.log(s);
  }
}
art(table.indexOf('一'));   // → 一條橫槓，右端有頓筆的小凸點
```

已逐字目視驗證：`阿 土 仔 一 十 口 八 九 日 邦` 全部正確。
（每個字右上／筆畫端點常有孤立的 1~2 px，那是明體的**頓筆襯線**，不是雜訊。）

### 這代表可以做什麼

- **換字**：把字表第 *i* 項換成別的 Big5 碼、同時換掉第 *i* 個 30-byte 字形，
  遊戲就畫得出原本畫不出來的字。兩邊都要改，因為 index 是共用的。
- **加字**：見 §8 —— `Run.exe` 裡**沒有**寫死 639。
- 現行編輯器只用到字表（做缺字檢查），字形部分還沒接進 UI。

> ⚠ `MEMDUMP.BIN` 在 `DOSBox-X/` 底下，而該目錄在 `.gitignore` 內（不進版控）。
> **不要刪掉它** —— 重抓一次要重跑遊戲。（不過字形本身已可從 `Wor.pak` 取得，
> 這份快照現在只剩「對照用」的價值。）

## 8. 找 639 的上限：`Run.exe` 裡沒有這個常數

結論先講：**639 / 638 / 1278 / 1664 / 19170 這些數字，在解壓後的 `Run.exe` 映像裡
一個都不是立即數。** 也就是說**沒有「上限」可以 patch** —— 字數是從資料本身推出來的。

### 怎麼確認的

把 205648 bytes 的映像掃過所有會帶 `imm16` 的編碼
（`3D`/`05`…`3D` 系列、`B8`~`BF` mov r16、`81 /r`、`C7 /r`、`68` push、`A9` test、
含 reg-direct 與 `disp16` 兩種 modrm 形式）：

| 值 | 命中 |
|---|---|
| 639 (`0x027F`) | **無** |
| 638 (`0x027E`) | 只有 `0x25D0` 的 `push 638`，緊接著 `push 640`——是座標之類的參數 |
| 1278 (`0x04FE`)＝字表位元組長度 | **無** |
| 1664 (`0x0680`)＝字形起點 | 只有 `0x43DF` 的 `push 0x680`，前後是 `push 0x67C/0x67E/0x682`——那是一串 DS 位址 |
| 19170 (`0x4AE2`)＝字形總長 | **無** |

執行期的資料段也掃過（DS 見下），整個 DGROUP 只有一處 word 等於 639（`DS:0x10FA`），
但它在 BSS、映像裡是 0，鄰居是一堆不相干的小數值，是普通遊戲變數。

### 過程中定出來的位址（之後做動態分析會用到）

| 項目 | 值 | 怎麼定出來的 |
|---|---|---|
| 映像載入位置 | 段 `0x075A`（linear `0x75A0`） | 拿映像裡的 32-byte 片段去 `MEMDUMP.BIN` 比對 |
| **DS** | **`0x3700`** | 資源記錄的 `+4` 欄位是它自己的 DS offset（見下），反推得 `0x3852C − 0x152C` |
| DGROUP 在映像的位置 | offset `0x2FA60` | `0x37000 − 0x75A0` |
| 換算式 | 程式碼裡的 `[imm16]` → 映像 offset `= 0x2FA60 + imm16` | |

### 資源區塊表（PAK 解壓後每一組的落點）

DS 裡有一條 **46 bytes/筆的鏈結串列**，記錄每個解壓出來的群組：

```
+0  word  offset（恆為 0）
+2  word  segment          ← 該組資料所在段
+4  word  下一筆記錄的 DS offset（＝自己的 offset + 0x2E）
+6  word  配置大小（段落數）
+8  byte  類別   +9 byte 01   +12 word 0002
+14 word  ≈ 資料長度/2
```

`Wor.pak` 六組的實際落點（這份快照）：

| 組 | 段 | 段落數 | 位元組 | 記錄位置 |
|---|---|---|---|---|
| g5 (106) | `5A59` | 9 | 144 | `DS:0x1614` |
| g2 (5482) | `5A62` | 388 | 6208 | `DS:0x15E6` |
| g3 (144) | `5BE6` | 10 | 160 | `DS:0x15B8` |
| g0 (2818) | `5BF0` | 182 | 2912 | `DS:0x158A` |
| **g4 字表 (1278)** | **`5CA6`** | 82 | 1312 | `DS:0x155C` |
| **g1 字形 (20836)** | **`5CF8`** | 1313 | 21008 | `DS:0x152E` |

**配置一律進位到段落，所以每組後面都有一段被清成 0 的餘裕。**
字表用 1278 bytes、配置 1312 bytes → 表尾之後有 **34 bytes 的 0**（已在快照中確認）。
這正好可以當 scan 的終止符，也解釋了為什麼引擎「知道」表在哪裡結束卻不用寫死長度。

### 順帶解開：`Wor.pak` g1 前 1664 bytes 是什麼

不是索引表，是**繪圖用的 run-length 查表**：258 個 u16 offset（516 bytes）+ 256 筆變長資料。
第 *n* 筆＝把位元組 *n* 的 8 個位元拆成交替的 0/1 連段長度，每筆總和恆為 8。

```
byte 0 = 00000000 → [8]        byte 4 = 00000100 → [5,1,2]
byte 1 = 00000001 → [7,1]      byte 5 = 00000101 → [5,1,1,1]
byte 2 = 00000010 → [6,1,1]    byte 6 = 00000110 → [5,2,1]
byte 3 = 00000011 → [6,2]      byte 7 = 00000111 → [5,3]
```

DOS 時代畫點陣字的標準加速手法（一次畫一整段而不是逐點）。
**它是定長 1664 bytes、與字數無關**，所以字形起點永遠是 `g1 + 1664`。

### ✅ 加字：兩組一起加長就會生效（已實測）

沒有常數要 patch，**兩組一起加長就會生效** —— 用「苗」「栗」實測，遊戲裡「苗栗縣」正常顯示。
做法：

1. `Wor.pak` g4 尾端加 2 bytes（新字的 Big5 碼）
2. `Wor.pak` g1 尾端加 30 bytes（該字的字形）
3. 重壓兩組、重算 PAK 指標表（`BASE 7 + value*2`，後面每組都要位移）

⚠ **仍然要留意的一點**：如果引擎是靠「表尾的 0」判斷結束，那新表尾之後必須還有 0。
配置是進位到段落的，正常會有餘裕（639→641 字時餘裕 14 bytes）；
但萬一新長度剛好落在段落邊界上，餘裕＝0，下一個區塊的內容就可能被當成字。
工具與編輯器都會在餘裕＝0 時出警告，多加或少加一個字就錯開了。

## 10. ✅ 「經過就觸發」找到了

原始追查目標（§0）終於有答案。**判斷在解壓映像 `0x1A5F`、檔案 `0x1C5F`，9 個位元組：**

```asm
1a5f: 26 83 3F 01   cmp word ptr es:[bx], 1   ; ← 01 = 銀行，寫死的
1a63: 74 03         je   0x1A68               ; 觸發
1a65: E9 69 00      jmp  0x1AD1               ; 不觸發
```

`es:[bx]` 指到的就是該地點的 SPECIAL 欄位。所以「只有銀行經過會觸發」不是什麼分派表，
就是一條 `cmp ==1`。

### 怎麼找到的（這條路以後還會用到）

§2 的教訓是「別猜跳轉表」，這次改成**從資料定址反推**：

1. 把三張圖 DSK 的地點資料解壓，拿 SPECIAL 欄位那段當特徵去 `MEMDUMP.BIN` 裡搜
   → 台灣的落在 `0x5502C`，所以地點區塊基底 = `0x54BC0`（段 `54BC:0000`）。
2. 掃全記憶體找指向它的 far pointer → 只有一個，在 **`DS:0x127A`**（DS 已知 = `0x3700`）。
3. 在映像裡搜 `mov si, 0x127a`（`BE 7A 12`）→ **93 處**，全都是同一個慣用法：

   ```asm
   mov ax, <欄位序號>
   imul word ptr [0x128c]      ; DS:0x128C = 283 = 記錄數
   add  ax, <locId>
   shl  ax, 1
   mov  bx, ax
   mov  si, 0x127a
   add  bx, [si+0xa]           ; 基底修正（值為 0）
   mov  es, [si+2]             ; 地點區塊的段
   mov  ax, es:[bx]
   ```

   → **位址 = 基底 + (欄位序號 × 283 + locId) × 2**，跟編輯器的 `LOC_FIELDS` 完全吻合
   （欄位 N 的偏移 = N × 566 = `0x236` × N）。
4. SPECIAL 是欄位 2，乘 2 會被編譯器優化成 `shl`，所以不是 `imul` 而是
   `mov bx,[0x128c]; shl bx,1`（`8B 1E 8C 12 D1 E3`）。**全映像只有 3 處**：
   - `0x1A4A` → `cmp ==1` ＝ **經過觸發**（本節）
   - `0x2957` → 前面有 `cmp [0x1098], locId` 的守門，是**踩上去**的處理
   - `0x29D3` → 存進 `[0x2EA]` 後 `call 0x340E`，特殊地點的分派器

> 💡 `DS:0x1AE` ＝ 目前地點編號、`DS:0x128C` ＝ 283、`DS:0x127A` ＝ 地點區塊的 far pointer。
> 要再挖任何跟地點欄位有關的邏輯，從這三個開始就對了。

### ❌ 改成區間判斷 —— 試過了，會當機

用同樣 9 個位元組換成範圍判斷（`mov ax,es:[bx]` / `sub al,LOW` / `cmp al,SPAN` /
`ja 0x1AD1`），編碼與跳距都對，**實測遊戲整個配色跑掉、擲骰後角色移動出界**。

原因不在編碼，在**對這段程式的理解錯了**：

> `cmp ==1` 成立後走到的 `0x1A68` **是銀行專屬的過路處理**，不是通用的特殊地點分派器。

那段做的事是：讀玩家記錄的欄位 11、比對 `[0x1082]`、擺出訊息 0xE3 的參數叫視窗、
再 `call 0x75E4`（又是一組寫死訊息 id 的視窗）。把別的種類放進來，等於讓公園/賭場
去跑銀行的流程，狀態當然壞掉。

**真正的分派器是 `0x340E`**，由 `0x29D3` 那條「踩上去」的路徑呼叫，而且呼叫前要先把
種類寫進 `[0x2EA]`。所以「經過就觸發任意種類」要做的是**在移動迴圈裡呼叫分派器**：

```asm
26 8B 07        mov ax, es:[bx]      ; 3   種類
2C <LOW>        sub al, LOW          ; 2
3C <SPAN>       cmp al, SPAN         ; 2
77 xx           ja  skip             ; 2   ── 到這裡就用掉 9 bytes 了
26 8B 07        mov ax, es:[bx]      ; 還需要：把種類寫進 [0x2EA]
A3 EA 02        mov [0x2ea], ax
E8 xx xx        call 0x340E
```

**9 個位元組放不下**，需要跳板到一塊沒被用到的空間（而且必須落在 EXEPACK 的原樣保留區
`0x0`~`0x29586` 內才 patch 得到，見 §1）。加上分派器本身可能假設「玩家已經停在那格」，
還得確認它會不會動到移動狀態。**這條路還沒走，編輯器目前不碰這 9 個位元組。**

<details>
<summary>當初那個（錯的）區間判斷編碼，留著備查</summary>

```asm
1a5f: 26 8B 07      mov ax, es:[bx]     ; ax = 種類（0~10，AH 恆為 0）
1a62: 2C <LOW>      sub al, LOW
1a64: 3C <SPAN>     cmp al, SPAN        ; SPAN = HIGH - LOW
1a66: 77 69         ja  0x1AD1          ; 不在範圍 → 不觸發（rel8 = 105，塞得下）
1a68:               （直接落下 ＝ 觸發）
```

- 種類低於 LOW 時 `sub al` 會借位變成大數，一樣被 `ja` 濾掉，所以兩條比較就表達得出閉區間。
- `AX` 在 `0x1A68` 立刻被 `mov ax,0xb` 覆蓋，clobber 安全。
- `LOW=1, SPAN=0` 與原版行為完全相同；寫回這個值時編輯器會直接還原成原本那條 `cmp`。
- **只做得到連續區間，不是任意組合** —— 9 個位元組放不下位元遮罩，而初始化資料落在
  EXEPACK 的壓縮尾段、沒辦法直接 patch（見 §1 的原樣保留區只到映像 `0x29586`）。


</details>

編輯器端已把 `readPassThrough()` / `writePassThrough()` 與對應 UI 全部移除；
`tests/editor.mts` 第 8 節守著「這 9 個位元組不得被動到」。

## 11. 「經過就觸發」續集：UNK13 是內建的「經過必停」（2026-08-03）

§10 收在「9 個位元組放不下，這條路還沒走」。這次走完了，結論跟原本預期的不一樣。

### ✅ 主結論：不用改 exe

**地點欄位 `UNK13`（欄位 0x13，offset `0x2A02`）是遊戲內建的「經過這格必須停下」旗標。**
移動迴圈有兩處在讀它：

```asm
1ae9: cmp word ptr es:[bx], 1     ; UNK13 == 1
1aef:   mov [0x1c6], 999          ;   停在這格
1af7:   把地圖上這格的圖塊清成 0
1b21:   把這格的 UNK13 清成 0      ;   一次性 → 地雷
1b3e: cmp word ptr es:[bx], 3     ; UNK13 == 3
1b44:   mov [0x1c6], 999          ;   停在這格，不清除 → 永久
```

`[0x1C6]` 是已走步數，設成 999 之後迴圈尾巴 `cmp ax,[0x1a6]; jg 離開` 立刻成立。
移動結束後遊戲照常跑「踩上去」的處理，**所以分派器是在正常狀態下被呼叫的**。

三張原版地圖的 UNK13 全部是 0，值 3 從來沒被用過。設成 3 就能讓任意特殊地點
「經過就觸發完整功能」，**`Run.exe` 一個位元組都不用動**。已實測。

工具：`node --import ./tests/loader.mjs tools/set-stopflag.mts <dsk> <locId> <0|1|3>`

> ⚠ 代價：剩下的步數會直接作廢，跟踩到路障一樣。

### ❌ 已推翻：移動途中呼叫分派器

- 只 `call 0x340E` → **花屏、不等輸入**。
- 連同「踩上去」的完整前置（`0x2957`~`0x29F1`，含 `lcall 0cc5:df9d` 與 `0cc5:9496`）
  整段抄進跳板 → **一樣**。

分派器要在「移動已經結束」的狀態下才會正常運作，跟前置無關。

### ✅ 已解：停下來觸發之後「續走剩下的步數」

`tools/patch-passthrough.mjs`，四個掛鉤點：

| 位置 | 條件 | 做什麼 |
|---|---|---|
| `0x1A5F` | 該格是特殊地點、表值=1、且**不是最後一格** | 記下剩餘步數 `[0x1a6]-[0x1c6]`，`[0x1c6]=999` 逼停 |
| `0x0CFE` / `0x1C0F` / `0x1D2E` | 還有步數要走 | **跳過** `lcall 0cc5:7d97`（畫靜止角色圖） |
| `0x29FF` | 還有步數要走 | `jmp 0x175F` 回到完整的移動前置 |
| `0x17B6` | 還有步數要走 | 拿剩餘步數當骰子填進 `[0x1a0]`、清旗標、`jmp 0x1831` |

**殘影的真因**：`lcall 0cc5:7d97`（依玩家欄位 0/1/2 畫靜止角色圖）**全檔有三個呼叫點**
（`0x0CFE`、`0x1C0F`、`0x1D2E`），一開始只擋了中間那個，所以另外兩處照畫。
三個都擋掉就乾淨了。

繞過的冤枉路（都無效，別再試）：續走前補 `lcall 0cc5:1348`、只擋 `0x1C0F` 一處、
續走改走完整前置、攔停時快照玩家欄位 9/0x11 再寫回。
另外 `0cc5:1144` **不是**「重畫一格」，是「把鏡頭移到 (x,y) 並重畫整張地圖」。

> 堆疊頂之上那段也是滿的，整個原始配額都在用。

| `src/core/exe.ts` | `loadExe`（EXEPACK 與未壓縮都吃）、`buildExe`、`readCap`/`writeCap`。**所有 offset 一律是映像 offset** |
| `src/core/passthrough.ts` | `insertPassThrough(x, table)`，六個掛鉤點 |
| `tools/unexepack.mts` | 倒出映像或未壓縮執行檔 |
| `tools/patch-passthrough.mts` | `--table 3=1,8=1` |
| `tools/set-stopflag.mts` | 改地點的 UNK13（不用改 exe 的那條路） |

`ExeImage` 自己記著 `inserted: { at, shift }`，所以 `readCap`/`writeCap` 在插跳板前後都能用，
呼叫端不用知道有沒有插過碼。存檔的順序是「原版映像 → 改容量 → 插跳板 → buildExe」，
每次都從 `Run.exe.bak`（原版）重建，patch 不會疊加。

> `Run.exe.bak` 現在是**正式的來源檔，不能弄丟**。
> （舊註解說「遊戲會把硬體偵測結果寫回 Run.exe，所以不能整檔還原」是誤判：
> `.bak` 與 `original/Run.exe` 逐位元組相同，跑過好幾次的執行檔與重建的版本也是 0 bytes 差異。）

### ⚠ 未壓縮版必須把 DOS 配額補 0（2026-08-03，實測踩過）

只把映像寫成未壓縮 MZ 是**不夠的**。壓縮版的解壓 stub 會先把自己搬到 DOS 配額的頂端
再解壓，所以「映像之上、配額之內」那塊留著它的殘骸——內容是垃圾，但每次都一樣。
未壓縮版沒有 stub，那塊就是 DOS 留下的前一支程式的殘骸，每次都不同。

實測症狀：**NPC 在股市會買一張又馬上全賣、在銀行會把錢存成負數，而且不是每次都發生**。
玩家自己操作時完全正常。填 0 之後就好了。

`buildExe` 現在會把 `minalloc` 那幾個段落也寫進檔案並填 0，然後把 minalloc 設成 0。
配額總量與壓縮版完全相同，只是改由檔案內容決定。

判斷這件事的方法（下次遇到類似問題可以照做）：做三個只差一個變因的執行檔，
壓縮+容量patch / 未壓縮+容量patch / 未壓縮+容量patch+跳板，一個一個試。

### 價格表與過路費（2026-08-03，查到一半）

價格表的 far pointer 在 `DS:0x11C2`、欄位 stride 在 `DS:0x11D4`。全檔只有 **7 處**讀它：

| 位置 | 用途 |
|---|---|
| `0x1DBE`~`0x1E09` | 地產價值 = 土地價格 + 房屋級數 × 增值價格 → `[0x1D8]` |
| `0x8AC7`~`0x8B2C` | 同上（地段從地點欄位 8 取得） |
| `0x23C7` | 增建費用（踩到自己的地） |
| `0x9660`~`0x968B` | **物價卡**：迴圈把 `[0x39E]` 加到前 44 個地段的土地價格上 |

> ⚠ **價格欄位 2~7（空地／一~五層過路費）沒有任何一處被這樣讀取。**
> `imul [0x11d4]` 全檔 0 處、`add ?x,[0x11d4]` 只有 3 處且都是欄位 0/1。
> 所以過路費要嘛用別的方式取得，要嘛編輯器「價格」頁對這幾個欄位的標示需要重新確認。
> 要繼續追的話，從玩家金錢區塊 `DS:0x11F0`（101 處存取）找轉帳的地方往回推。

地點欄位的存取點分布（`mov ax,<欄位>; imul [0x128c]`）：
SPECIAL×7、所有者×8、房屋級數×2（`0x23A4` 增建、`0x267C` 級數>3 的訊息）、
預約×3、UNK13×8、UNK3×2。

### 資產總值的算式與執行期結構（2026-08-03，拿記憶體快照驗過）

`財產查詢` 的資產總值：

```
資產總值 = 現金 + 存款 + Σ(土地價格 + 房屋級數 × 增值價格) + 股票市值
```

實測玩家 0：`190037 + 19691077 + 81950 = 19963064`，與畫面完全吻合（他沒買股票）。
其餘 NPC 對不上，差額 80 萬~170 萬，那就是股票市值。

> ⚠ **地點的 `OWNER` 欄位是 1-based**：0=無主，1~N 對應玩家 0~N-1。
> 用 0-based 去算會把每個人的地產算成別人的。

執行期的結構（這一份快照，DS = `0x3718`，linear `0x37180`）：

| DS offset | 內容 |
|---|---|
| `0x1194` | 玩家記錄（u16，stride = 玩家數 `[0x11A6]`） |
| `0x11C2` | 價格表（u16，stride = `[0x11D4]`，實測 45） |
| `0x11F0` | **金錢：u32[欄位][玩家]，欄位 0=現金、欄位 1=存款**，每欄 6 個玩家 |
| `0x127A` | 地點區塊（u16，stride = `[0x128C]` = 283） |
| `0x1096` | 這張圖的地點上限 |

定 DS 的方法：拿地圖 DSK 的 SPECIAL 欄位那 566 bytes 當特徵去快照裡搜，得到地點區塊
的位址；再搜指向它的 far pointer，那個位址就是 `DS + 0x127A`。

> 過路費欄位（價格欄位 2~7）**在記憶體裡是有值的**（地段 1：120/360/900/3000/4200/6000），
> 所以編輯器的標示正確。但引擎讀它的地方還沒找到——`mov si,0x11c2` 只有 6 處、
> `imul [0x11d4]` 0 處。推測是某處載入 si 之後重複使用、用不同的索引算式取欄位 2~7。

### ⚠ 測試時的 DOSBox cycles（2026-08-03，繞了一大圈才發現）

`DOSBox-X/dosbox-x.conf` 預設 `cycles = 64000`（約 486DX2-66 以上）。這個速度會讓
遊戲出現**與程式修改無關**的假象：

- **開場動畫有一條橫向花屏**（只花底圖、精靈不受影響）——1993 年的遊戲寫 VGA 記憶體
  時沒等 retrace，機器太快就會撞上正在掃描的那一列
- **走幾步就當機**

拿**完全未改的原版** `Run.exe.bak` 一測，同樣會花屏；把 cycles 調回 8000 左右就都正常了。

**2026-08-03 又被騙了第二次**：NPC 突然破產、股市市值冒出莫名的 200——重開 DOSBox
並降速之後全部消失。當時我正在改物價指數，差點把它歸咎於自己剛改的那一條指令。

> 追任何「遊戲行為怪怪的」問題之前，**先確認 cycles 是period-appropriate 的值**，
> 不然會把 DOSBox 的時序假象當成自己的 bug 追。（本專案的自動開機測試只檢查
> 「開得起來」，是在 64000 下跑的，看不出這類問題。）
> `core = dynamic_x86` 在高 cycles 下也會放大這類問題，必要時改 `core = normal` 再確認。

## 12. 物價指數（2026-08-03，已實作並實測）

「所有玩家的總資產每超過一個門檻，過路費就多一倍」，等差、只漲不落。
實作在 `src/core/priceindex.ts`，掛在**引擎讀過路費唯一的那一處**。

### 過路費的讀取點：全映像只有 `0x12695`（段 0xCC5）

```asm
1267E: add ax, 2              ; 價格欄位序號 = 房屋級數 + 2（空地=2…五層=7）
12681: imul word [0x11d4]     ; × 價格表 stride　← 全映像唯一一處
1268C: mov si, 0x11c2         ; 價格表
12695: mov ax, es:[bx]        ; ← 過路費（表裡是 u16）
12698: cdq                    ; 符號延伸成 DX:AX
12699: add ax,[bp-0x18]       ; 32-bit 累加
1269C: adc dx,[bp-0x16]
```

外層是「走訪所有地點、把某地主的過路費加總」的迴圈，函式進入點 `0x125CD`
（段內 `0x597D`），`retf 2`、以 `DX:AX` 回傳，**全映像只有 `0x156DE` 一個呼叫點**。
實測收租確實走這條路（改了倍率之後踩空地收的錢就跟著變），而且**作用範圍是隔離的**——
指數 37 的錯誤版本只影響過路費，AI、股市、其他系統都沒事。

掛鉤方式：把 `mov ax,es:[bx]` + `cdq`（4 bytes）換成一條 near jmp，跳板裡做
`mov ax,es:[bx]` → 算指數 → `imul cs:[INDEX]` → 跳回 `0x12699`。
**`cdq` 與 `imul r/m16` 都是把結果放進 DX:AX，語意直接接得上**，後面的 32-bit
`add/adc` 一個字都不用改——這是這個掛鉤點最漂亮的地方。

溢位不是問題：表裡單格是 u16（上限 65535），但累加與回傳全程 32-bit。

### 總資產的算式

遊戲「財產查詢」的資產總值，實測分解如下（2026-08-03，四家同一時刻的讀數）：

| 玩家 | 現金 | 存款 | 股票 | 現+存+股 | 資產總值 | 差（＝地產） |
|---|---|---|---|---|---|---|
| 0 | 549200 | 62400 | 0 | 611600 | 627800 | 16200 |
| 1 | 158195 | 385827 | 234995 | 779017 | 797517 | 18500 |
| 2 | 0 | 200214 | 103676 | 303890 | 315290 | 11400 |
| 3 | 110805 | 346496 | 268347 | 725648 | 743883 | 18235 |

```
資產總值 = 現金 + 存款 + 股票市值 + 地產
指數     = 1 + 總資產 ÷ 門檻          （門檻以「千元」為單位，可編輯）
INDEX    = max(INDEX, 指數)           （只漲不落）
```

跳板目前只算 **現金 + 存款 + 股票**（地產佔比約 1%，使用者確認不需要）。

### ⚠ 未解：股票那一段完全沒算到

實測（門檻 10 千元、關掉最高水位，讓倍率直接讀出算出來的總額）：

```
四家現金＋存款 = 1,813,137     ← 量到的倍率換算回來是 1,755,000~1,845,000，吻合
四家股票       =   607,018     ← 這一段沒有進到總額裡
```

反組譯確認那段迴圈的機器碼與意圖**逐條吻合**（`mov bx,[di]`、`mov di,0x1E0`、
`es:[bx+di]` 都對），所以不是編碼問題，是**「持股在欄位 19+N」這個假設有問題**。

那個假設是從兩個樣本推的（第 6 支台塑 → 欄位 25、第 8 支新光 → 欄位 27），
兩點都落在同一小段，推出來的規律不一定成立。**下一步**：用
`insertPriceIndex(x, { only: 'stocks', thresholdK: 10, noHighWater: true })`
量出股票那一段實際算出多少——

- 倍率 ≈ 61 → 股票算對了，缺口在別處
- 倍率 = 1 → 完全沒找到，得重新定位持股陣列
- 其他 → 只找到一部分，從差額反推漏了哪幾支

如果是「完全沒找到」，用四家的股票市值（已知數）去記憶體快照裡搜
「張數 × 股價 = 該值」的組合，可以一次釘死，不必再靠推論。

### 診斷開關

`PriceIndexOptions` 有三個只給查錯用的欄位，**刻意留在程式碼裡**——
今天證明「把變因切開」比猜有效太多：

| 欄位 | 作用 |
|---|---|
| `fixedIndex` | 指數寫死，跳板裡完全不放資產計算。用來確認「乘法掛鉤點」本身是乾淨的 |
| `noHighWater` | 不套「只漲不落」，倍率直接反映當下算出來的值 |
| `only` | 只算 `'cash'` 或 `'stocks'` 其中一項，量出各項各自貢獻多少 |

搭配 `thresholdK: 10` 時，`倍率 = 1 + 算出來的總額 ÷ 10000`，
等於把跳板內部的中間值**當成讀數印出來**——這個遊戲沒有 debugger 可用，
這是目前最有效的觀測手段。

### ⚠ 資源記錄的 `+0xA` 不是基底位址

遊戲存取資源區塊的慣用法是：

```asm
mov si, 0x11f0
add bx, [si+0xa]      ; ← 這不是基底！
mov es, [si+2]
```

`+0xA` 實測是 **65532 = −4**，是給「陣列從 1 起算」用的修正值。真正的基底在 `+0`（值是 0）。
照抄慣用法會讓整個區塊往前偏 4 bytes，讀到相鄰結構的垃圾——實測總資產被算成 1800 萬
（正確是 214 萬），指數變成 37。

> 這個 bug 花了很久才抓到，因為**我的 JS 模擬用 `+0`、組語用 `+0xA`**，
> 模擬跑出正確答案反而讓我以為組語沒問題。
> **教訓：模擬要模擬「實際發出的指令」，不是模擬「我以為的意圖」。**

### 診斷開關 `fixedIndex`

`insertPriceIndex(x, { fixedIndex: 2 })` 會產生一個**只有一條 `imul`、指數寫死、
跳板裡完全沒有資產計算**的版本。用來把「乘法掛鉤點」與「資產計算」兩個變因切開——
今天就是靠它證明掛鉤點是乾淨的，把範圍縮到計算那一段。這個開關留在程式碼裡。

### 插碼機制：`src/core/codecave.ts`

段界插碼抽成了通用原語，可以連續插多塊：

```ts
segmentEnds(x)              // 所有段界（0x0CC5、0x1C6A、…）
assertPadded(x, atPara)     // 段界前必須是補 0
insertBlock(x, atPara, blk) // 插入 + 修重定位項位址/段值 + 修 CS/SS + 記錄位移
```

`ExeImage.inserts[]` 用**原版座標**記每次插入，`imageOffset()` 負責換算，
`toOriginal()` 是反向。跳板裡的簽章存的是「塊數 + 每塊(位址,長度)」，
所以寫出去再讀回來，多塊的位移一樣還原得出來。

> ⚠ **映像 offset ≠ 段內 offset。** 第一塊跳板在段 0，兩者剛好相等；第二塊在段 0xCC5，
> 相差一個段基底。`cs:[變數]` 這種絕對定址一定要用段內 offset，不然會讀到別的地方。
> 相對跳轉不受影響（差值在兩種座標下相同）。
